# World-Class Engineering — 思考の強制装置

## Critical: このSkillの目的

このSkillは「コードの書き方」を定義するものではない。
**「コードを書く前に何を考えるべきか」を強制する装置**である。

世界トップのエンジニア（Evan You, Linus Torvalds, Dan Abramov, TJ Holowaychuk）に共通する特性は、
**実装する前に頭の中で完全なシミュレーションを終わらせている**ことである。
コードを書く行為は、思考の「出力」に過ぎない。

> **絶対原則: 「たぶんこれが原因だろう」で修正を開始することを禁止する。**
> 「なぜこの問題が起きているのか」を論理的に証明してから、初めてコードに触れよ。

---

## Important: 4フェーズ思考フレームワーク

すべての実装作業は、以下の4フェーズを**順序厳守**で通過しなければならない。
フェーズを飛ばすことは禁止。各フェーズの完了条件を満たさない限り、次のフェーズに進んではならない。

### Phase 1: DIAGNOSE（診断）

**目的**: 問題の根本原因を特定する。「何が起きているか」ではなく「なぜ起きているか」を解明する。

**必須アクション**:
1. **現象の正確な記述**: ユーザーが報告した症状を、主観を排除して事実だけで記述する
2. **環境情報の収集**: OS、ブラウザ、バージョン、ネットワーク状況など、再現に必要な全情報を特定する
3. **仮説の列挙**: 考えうる原因を最低3つ列挙する（1つだけに飛びつくことを禁止）
4. **仮説の検証**: 各仮説を、コードを変更せずに検証する方法を考え、実行する
5. **根本原因の確定**: 検証結果に基づき、根本原因を1つに絞り込む

**完了条件**: 「この問題は○○が原因で発生している。なぜなら△△を検証した結果、□□が確認されたからである」と、**証拠付き**で説明できること。

**禁止事項**:
- 「たぶん○○が原因だろう」という推測だけで次のフェーズに進むこと
- コードを変更して「動くかどうか試してみる」こと（Phase 1ではコードに触れない）
- ユーザーの環境情報を確認せずに仮説を立てること

---

### Phase 2: DESIGN（設計）

**目的**: 根本原因に対する最適な解決策を、複数案の比較から論理的に選択する。

**必須アクション**:
1. **解決策の列挙**: 最低2つの解決策を提示する（1案のみは禁止）
2. **トレードオフの明記**: 各解決策について「利点」「欠点」「リスク」を明記する
3. **エッジケースの洗い出し**: 解決策が失敗しうるケース（異なるブラウザ、特殊文字、大量データ等）を列挙する
4. **最適解の選択根拠**: なぜその解決策を選んだのかを、論理的に説明する

**完了条件**: 「解決策Aを選択する。理由は、解決策Bと比較して○○のトレードオフが優れているため。ただしエッジケース△△には注意が必要」と説明できること。

**禁止事項**:
- 思いついた最初の解決策をそのまま実装すること
- トレードオフを検討せずに「これが正しい」と断定すること

---

### Phase 3: IMPLEMENT（実装）

**目的**: Phase 2で選択した解決策を、最小限の変更で正確に実装する。

**必須アクション**:
1. **変更範囲の最小化**: 修正するファイル・行数を最小限に抑える
2. **変更の意図をコメントで記述**: なぜこの変更が必要なのかをコード内コメントで説明する
3. **エッジケースへの対応**: Phase 2で洗い出したエッジケースすべてに対応していることを確認する

**完了条件**: 「この変更は、Phase 1で特定した根本原因○○を、Phase 2で選択した解決策△△によって解決する。エッジケース□□にも対応済み」と説明できること。

**禁止事項**:
- Phase 2で選択していない解決策を突然実装すること
- 「ついでに」関係ない修正を混ぜること

---

### Phase 4: VERIFY（検証）

**目的**: 修正が**ユーザーの実環境で**正しく動作することを証明する。

**必須アクション**:
1. **自環境での検証**: まず自分の環境で動作確認する
2. **ユーザー環境の再現**: ユーザーのブラウザ・OS・設定を可能な限り再現して検証する
3. **「なぜ動くのか」の説明**: 「動いた」ではなく「○○の理由で正しく動作する」と説明できること
4. **エッジケースの検証**: Phase 2で列挙した全エッジケースをテストする
5. **ユーザーへの検証依頼**: 最終的にはユーザー自身に確認してもらい、結果を受け取る

**完了条件**: ユーザーから「問題が解決した」という明示的なフィードバックを受け取ること。自分のテスト結果だけで「完了」と宣言することを禁止する。

**禁止事項**:
- 自分のテスト環境で動いただけで「修正完了」と報告すること
- ユーザーからのフィードバックを待たずに次のタスクに移ること

---

## Important: 失敗時のエスカレーション・プロトコル

修正が失敗した場合（ユーザーから「直っていない」と報告された場合）：

1. **即座にPhase 1に戻る**（Phase 3の微調整で済ませることを禁止）
2. **前回の仮説が間違っていた理由を明記する**
3. **前回と同じアプローチの変形を試みることを禁止する**（根本的に異なるアプローチを検討する）
4. **失敗の記録を `references/failure-log.md` に追記する**

> **2回連続で修正に失敗した場合**: ユーザーの実環境で直接デバッグ情報を収集する手段を最優先で検討せよ。推測による修正を繰り返すことは、信頼の毀損を加速させるだけである。

## Examples

### Example 1: 新機能の実装
User says: 「ファイルのダウンロード機能を追加して」
Actions:
1. Phase 1: ダウンロード機能の要件を確認。対象ブラウザ・OS・ファイル形式を特定
2. Phase 2: Blob URL方式 vs Data URI方式 vs サーバーサイド生成方式を比較。各ブラウザの対応状況を調査
3. Phase 3: 選択した方式で実装。ファイル名のサニタイズ、MIME typeの設定を含む
4. Phase 4: ユーザーの実ブラウザで全フォーマットのダウンロードを検証
Result: 1回の実装で正しく動作する成果物

### Example 2: バグ修正（修正が失敗した場合）
User says: 「直っていない」
Actions:
1. Phase 1に強制リターン。「前回の仮説は○○だったが、△△の理由で誤りだった」と記述
2. ユーザーの実環境情報を再収集（ブラウザのDevToolsログ、コンソールエラー等）
3. 新しい仮説を最低3つ立て、コードを変更せずに検証
4. failure-log.md に前回の失敗を記録
Result: 根本原因の正確な特定と、確実な修正

## Troubleshooting

### 「たぶんこれが原因だろう」で修正してしまった
症状: Phase 1を飛ばして直接コード修正に入ってしまった
原因: 「速く直したい」という焦りが思考プロセスを短絡させた
対処: 修正を巻き戻し、Phase 1から再開する。焦りは品質の敵である

### 修正が2回以上失敗した
症状: 同じバグに対して複数回の修正試行が必要になった
原因: Phase 1の診断が不十分。根本原因ではなく表面的な症状を修正している
対処: ユーザーの実環境から直接デバッグ情報を収集する。推測を止め、事実に基づく

### 自分のテストでは動くがユーザー環境では動かない
症状: テストエージェントでは正常だがユーザーが「直っていない」と報告
原因: テスト環境とユーザー環境の差異（ブラウザバージョン、設定、キャッシュ等）
対処: ユーザーのブラウザでJavaScriptコンソールログを確認する手段を確立する。推測ではなく実データに基づく診断を行う
